# CodeMemGovernor: Coding Agent 上下文与记忆治理层

## 1. 项目背景
在构建 Coding Agent 时，随着多轮交互和工具调用（如文件读取、终端执行），上下文会迅速膨胀。这不仅导致 API 成本剧增，还会让模型陷入“金鱼记忆”，甚至触发大模型平台（如百炼）的输入长度硬限制而直接崩溃。
本项目是一个**模型无关**的上下文治理中间件（Governor），在不修改底层模型的前提下，通过拦截并处理 Agent 与大模型之间的消息流，实现成本与性能的双重优化。

## 2. 核心治理策略
治理层位于 `Agent Loop` 与 `LLM API` 之间，包含以下四大机制：
*   **滑动窗口裁剪**：当历史消息超过阈值时，自动丢弃中间冗余对话，但强行保留“系统提示词”和包含“硬约束（如禁止某操作）”的用户指令，并动态生成历史摘要衔接，防止任务断层。
*   **文件读取折叠 (File Collapse)**：若同一文件被多次读取，旧内容将被替换为极短的占位符，仅保留最新一次读取结果。大幅降低 Coding 场景的 Token 消耗。
*   **超长输出截断 (Result Truncation)**：单次工具返回结果严格限制在 5000 字符以内，彻底杜绝因终端海量输出导致的 API 400 字符超限崩溃。
*   **子代理隔离 (Subagent Isolation)**：拦截主 Agent 的重型探索命令（如 `find`, `cat`），派发给独立上下文的小弟（子代理）执行。子代理仅向主 Agent 返回提炼后的结构化总结，避免“垃圾信息”污染主上下文。

## 3. 效果量化 (A/B Test)
在执行相同复杂度的长任务（需多轮读取 200+ 行文件并配合终端执行）下：
*   **无治理层 (Baseline)**：Input Tokens = `35,756` | Total = `36,353`
*   **有治理层 (Governor)**：Input Tokens = `21,509` | Total = `22,459`

**结论：在保证任务成功率的前提下，单次任务的输入 Token 消耗降低了 38%。**

## 4. 工程踩坑记录 (Challenges)
*   **跨平台兼容性**：大模型自带“Linux 偏科”，在 Windows 环境下强推 `ls/find`。治理层在工具层加入了严格的 OS 提示词注入与 `TimeoutExpired` 超时捕获，并强制使用 UTF-8 解码，完美兼容本地环境。
*   **死循环阻断**：子代理探索失败时，主代理容易陷入“无限重试”。通过限制子代理最大迭代次数并强制返回兜底摘要，成功阻断 Token 消耗黑洞。

## 5. 快速启动
1. 配置 `.env`（参考 `.env.example`）
2. 运行对比测试：
   - 无治理版：`uv run python scripts/run_agent.py --no-gov`
   - 开启治理：`uv run python scripts/run_agent.py`
